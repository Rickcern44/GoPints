## Purpose

Defines automated, PR-less releases: a push to `main` that contains releasable changes for a package tags and publishes that package's release directly, with stable versions only and nothing committed back to the repository.

## Requirements

### Requirement: Main is the release trigger
A push to `main` touching a package's files SHALL release that package if, and only if, Conventional Commits that touched the package's path since its last `<package>-v*` tag warrant a version bump (`fix` → patch, `feat` → minor, breaking change → major). No release pull request SHALL be opened.

#### Scenario: Releasable commit lands on main
- **WHEN** a push to `main` includes a `feat:` commit touching `web/` since `web`'s last tag
- **THEN** a `web-vX.Y.Z` tag (minor bump) and GitHub Release are created at the pushed commit, and `web`'s image is built and pushed

#### Scenario: Only non-releasable commits
- **WHEN** a push to `main` contains only `chore:`, `docs:`, or similar commits for a package
- **THEN** no tag, release, or build occurs for that package

#### Scenario: Cross-cutting commit
- **WHEN** a releasable commit touches both `gopints/` and `web/`
- **THEN** both packages are released independently, each at its own next version

### Requirement: Stable versions only
Computed versions SHALL be plain `MAJOR.MINOR.PATCH` semver; the pipeline SHALL NOT produce pre-release or build-metadata suffixes.

#### Scenario: Version computed
- **WHEN** the next version is computed for a package
- **THEN** it matches `^[0-9]+\.[0-9]+\.[0-9]+$`

### Requirement: Release notes live in the GitHub Release
Release notes SHALL be generated by git-cliff from only the commits scoped to the package's path since its last tag and published as the GitHub Release body. The pipeline SHALL NOT commit changelog or version files back to `main`.

#### Scenario: Release published
- **WHEN** a package is released
- **THEN** the GitHub Release body contains that package's notes, and no commit is pushed to `main` by the pipeline

### Requirement: Releases are serialized and recoverable
Release runs SHALL be serialized so each sees previously created tags, and artifacts for an existing tag SHALL be re-publishable manually.

#### Scenario: Build failed after tagging
- **WHEN** a release's artifact build fails after its tag was created
- **THEN** a manual workflow run with that tag name re-publishes the artifacts without creating a new tag
